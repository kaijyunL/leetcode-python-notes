# LeetCode 8. 字符串转换整数（atoi）解析

## 题目描述

请你实现一个 `myAtoi(s)` 函数，把字符串转换成一个 32 位有符号整数。

转换规则大致如下：

1. 跳过前导空格
2. 读取一个可选的正负号
3. 继续读取后面的连续数字
4. 遇到非数字字符就停止
5. 如果结果超出 32 位有符号整数范围，就截断到边界

32 位有符号整数范围是：

```text
[-2147483648, 2147483647]
```

例如：

```text
s = "   -42"
```

返回：

```text
-42
```

---

## 先理解题意

### 1. 这题不是单纯“转整数”，而是在做一套解析流程

很多人第一次看这题，会觉得它只是把字符串转成整数。

其实不是。

这题真正考的是：

```text
你能不能严格按题目规定的顺序，一步一步解析字符串
```

因为这里不是“只要字符串里有数字就拿来用”。

而是必须按下面这条固定流程走：

- 先跳过前导空格
- 再看有没有符号
- 再读连续数字
- 一旦遇到不合法字符，立刻停下

顺序不能乱。

### 2. 核心难点在“什么时候停”和“怎么处理越界”

这一题最容易写乱的地方，不是正负号本身，而是两个细节：

- 到底哪些字符应该继续读
- 数字越来越大时，什么时候该截断

比如：

```text
"4193 with words"
```

应该读出 `4193`，遇到空格就停。

而：

```text
"words and 987"
```

因为开头第一个有效字符就不合法，所以直接返回 `0`。

也就是说，这题不是“尽量找数字”，而是：

```text
只有当前流程允许读数字时，才继续读
```

### 3. 最自然的三条思路

看到这题，一般最自然会想到三种写法：

1. **手动模拟**：按题目规则一步一步写
2. **正则表达式**：直接匹配开头那段合法数字串
3. **有限状态机**：把整套解析流程写成状态转移

这三种方法正好对应：

```text
先把题意写清楚，再用工具简化，最后上升到更体系化的建模方式
```

---

## 方法一：手动模拟（面试主推）

这是最适合面试的方法。

### 思路

这题最稳的写法，就是老老实实按题目步骤来。

我们用一个指针 `i` 从左到右扫描字符串：

1. 先跳过所有前导空格
2. 判断当前位置是否有 `+` 或 `-`
3. 然后开始读取连续数字
4. 每读到一位，就用 `ans = ans * 10 + digit` 更新结果
5. 在更新前先判断是否会越界，如果会就直接返回边界值

### 为什么可行

因为题目本来就是一套顺序解析规则。

手动模拟的好处是：

```text
题目怎么规定，我们就怎么执行
```

逻辑完全贴题意，不需要额外抽象。

### 手推一个例子

看：

```text
s = "   -42abc"
```

处理过程是：

1. 先跳过前面的空格
2. 读到 `-`，记下结果是负数
3. 继续读 `4`、`2`
4. 读到 `a` 时停止

于是最终结果就是：

```text
-42
```

### 为什么它最适合面试

1. 完全贴合题意，最好解释
2. 每一步都能单独讲清楚
3. 边界条件都能自然展开
4. 不依赖额外库或高级抽象

### 代码

对应代码文件：

```text
02_字符串/12_q8/solution_1_simulation.py
```

### 复杂度

- 时间复杂度：`O(n)`
- 空间复杂度：`O(1)`

### 关键细节

#### 1. 为什么要先跳过前导空格

因为题目明确说了，只有前导空格可以忽略。

如果一开始不先处理它们，后面的符号和数字判断都会错位。

#### 2. 为什么越界最好在构造数字时就判断

因为一旦数字真正构造出来，可能已经超过 32 位范围了。

提前判断能让逻辑更稳，也更符合“模拟系统处理输入”的感觉。

#### 3. 为什么读到第一个非数字字符就停

因为题目只允许读取“开头那一段合法数字串”。

后面的内容无论是什么，都不再参与转换。

## 方法二：正则表达式

### 思路

如果只从“匹配规则”角度看，这题其实就是想要提取：

```text
去掉前导空格后，开头那一段可选符号 + 连续数字
```

于是可以直接用正则来匹配：

```text
[+-]?\d+
```

然后把匹配结果转成整数，再做边界截断。

### 为什么可行

因为题目要求的那段合法前缀，本身就很适合用模式匹配表示。

正则在这里做的事情，本质上是：

```text
把“开头合法片段”的定义直接写出来
```

### 复杂度

- 时间复杂度：通常记作 `O(n)`
- 空间复杂度：`O(1)` 到 `O(n)` 之间，取决于实现细节

### 评价

优点：

- 写法很短
- 很适合快速验证规则

缺点：

- 面试里解释过程不如手动模拟自然
- 有点借助语言工具“跳过过程”

## 方法三：有限状态机（DFA）

### 思路

这题本质上就是在读一个字符流。

而这种“根据当前状态和当前字符类型决定下一步怎么走”的问题，非常适合用有限状态机来描述。

我们可以把整个过程拆成四种状态：

- `start`：还在处理前导空格
- `signed`：已经读过符号
- `in_number`：正在读数字
- `end`：解析结束

然后再把字符分成四类：

- 空格
- 正负号
- 数字
- 其他字符

这样每读一个字符，都只是做一次状态转移。

### 为什么可行

因为题目规则本来就有明显的阶段性。

状态机只是把这种“当前阶段允许读什么、不允许读什么”的关系，系统地写出来。

### 一个核心理解

比如在 `start` 状态下：

- 读到空格，还留在 `start`
- 读到符号，转到 `signed`
- 读到数字，转到 `in_number`
- 读到其他字符，直接结束

这其实就是把题目规则翻译成了表格和状态转移。

### 复杂度

- 时间复杂度：`O(n)`
- 空间复杂度：`O(1)`

### 评价

优点：

- 结构非常清晰
- 适合处理更复杂的字符流解析问题
- 容易扩展

缺点：

- 对这题来说略显“重”
- 面试里第一次写，成本通常高于方法一

## 哪个方法最适合面试

### 结论

**最适合面试的是：方法一，手动模拟。**

### 为什么

1. 和题目流程最一致
2. 边界条件最容易讲清楚
3. 不依赖语言特性
4. 代码长度和稳定性都很合适

### 方法二的价值

方法二的价值在于：你可以从“规则匹配”的角度重新理解题意。

它很适合作为一个更短的补充解法。

### 方法三的价值

方法三更像进阶视角。

它能帮助你把这题看成一个标准的“字符流状态转移”问题，而不只是某道具体题。

## 最后总结

这题最重要的主线就是：

1. 它考的不是“会不会转整数”，而是能不能严格按规则解析字符串
2. 真正关键的是前导空格、符号、连续数字和越界处理这几步的顺序
3. 面试最稳的写法是手动模拟
4. 如果再往上抽象，这题本质上也可以看成一个状态机问题

如果你能把这句复述清楚：

> **这题本质上是在按固定流程解析字符串，核心是只读取开头那段合法数字前缀，并在构造结果时正确处理符号和越界。**

那这题就算真的掌握了。
