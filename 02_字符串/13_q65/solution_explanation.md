# LeetCode 65. 有效数字（Valid Number）解析

## 题目描述

给你一个字符串 `s`，请你判断它是否表示一个**有效数字**。

这里的“有效数字”不是随便包含几个数字字符就算。

它需要满足题目规定的格式规则，比如：

- 可以有可选的正负号
- 可以有小数点
- 可以有指数部分 `e` 或 `E`
- 指数后面必须是整数

例如：

```text
"2"        -> True
"-0.1"     -> True
"4."       -> True
"2e10"     -> True
"99e2.5"   -> False
"1e"       -> False
```

---

## 先理解题意

### 1. 这题不是看“像不像数字”，而是检查格式是否合法

很多人第一次看这题，会凭直觉判断：

```text
这个字符串看起来像数字吗？
```

但面试里不能靠“看起来像”。

这题真正考的是：

```text
你能不能把数字格式规则拆清楚，并严格执行
```

比如：

- `4.` 是合法的，因为有整数部分，小数部分可以为空
- `.1` 是合法的，因为小数点后面有数字
- `.` 不合法，因为小数点前后都没有数字
- `1e10` 合法，但 `1e` 不合法，因为指数后面必须有数字

所以这题本质上是一个**格式验证**问题。

### 2. 真正难的不是字符本身，而是“字符出现的位置”

单看每个字符都很简单：

- 数字
- `+` / `-`
- `.`
- `e` / `E`

难点在于：

```text
某个字符不是能不能出现，而是它能不能出现在当前位置
```

比如：

- `+` 只能在开头，或者紧跟在 `e/E` 后面
- `.` 只能出现一次，而且不能出现在指数部分后面
- `e/E` 只能出现一次，并且前后都必须有数字

也就是说，这题核心不是记字符，而是记：

```text
到当前位置为止，之前已经出现过什么
```

### 3. 最自然的三条思路

看到这题，一般最自然会想到三种写法：

1. **手动模拟**：从左到右逐个字符检查规则
2. **正则表达式**：直接把合法格式写成匹配模式
3. **有限状态机**：把整个过程写成状态转移

这三种方法正好对应：

```text
先直接按规则判断，再用模式表达，再上升到更系统的建模方式
```

---

## 方法一：手动模拟（面试主推）

这是最适合面试的方法。

### 思路

从左到右扫描字符串，并用几个标志位记录当前已经见过什么：

- `has_digit`：是否已经见过数字
- `has_dot`：是否已经见过小数点
- `has_e`：是否已经见过指数符号

然后对每个字符分类讨论：

1. 遇到数字，说明当前这一段至少有了有效数字
2. 遇到 `+/-`，只能在开头，或紧跟在 `e/E` 后面
3. 遇到 `.`，不能重复出现，也不能出现在指数部分后
4. 遇到 `e/E`，不能重复出现，而且它前面必须已经有数字
5. 遇到 `e/E` 后，要重新要求后面再出现数字，所以把 `has_digit` 重新置为 `False`

最后扫描结束时，只要当前状态下已经见过数字，就说明格式合法。

### 为什么可行

因为这题的规则，本质上就是“某些字符有没有出现过、能不能在当前时刻出现”。

而标志位法正好直接维护这些信息。

它的核心思想是：

```text
边扫描，边记录当前格式状态
```

不需要额外复杂结构，逻辑非常贴题。

### 手推一个例子

看：

```text
s = "-123.45e+6"
```

扫描过程可以这样理解：

1. 先看到 `-`，合法，因为它在开头
2. 接着读到数字，`has_digit = True`
3. 看到 `.`，合法，因为此前没出现过小数点，也还没进入指数部分
4. 继续读数字
5. 看到 `e`，合法，因为前面已经有数字
6. 这时把 `has_digit` 重置成 `False`，表示指数部分还必须再读到数字
7. 看到 `+`，合法，因为它紧跟在 `e` 后
8. 再读到 `6`，于是指数部分也有数字了

最终结果合法。

### 为什么它最适合面试

1. 完全贴着题意走，最好讲
2. 规则拆解过程很自然
3. 不依赖正则和复杂状态表
4. 现场出错后也更容易排查

### 代码

对应代码文件：

```text
02_字符串/13_q65/solution_1_simulation.py
```

### 复杂度

- 时间复杂度：`O(n)`
- 空间复杂度：`O(1)`

### 关键细节

#### 1. 为什么遇到 `e/E` 后要把 `has_digit` 重新置为 `False`

因为指数部分后面必须还要再有数字。

比如：

```text
"1e"
```

如果不重置，你会误以为前面的 `1` 已经足够了。

#### 2. 为什么 `.` 不能出现在 `e/E` 后面

因为指数部分本身必须是整数，不能再带小数点。

所以像：

```text
"99e2.5"
```

一定是不合法的。

#### 3. 为什么最后返回的不是 `True`，而是 `has_digit`

因为像：

```text
"+"
"."
"1e"
```

这些字符串在扫描中途都不一定立刻报错，但结束时仍然没有形成一个完整的数字。

所以必须用“最后有没有真正读到数字”来收尾。

## 方法二：正则表达式

### 思路

如果把题目看成一个纯格式匹配问题，那就可以直接把合法数字的结构写成正则。

整体可以拆成两部分：

1. 主体部分：整数或小数
2. 可选的指数部分：`e/E + 可选符号 + 整数`

也就是说，可以写成类似：

```text
[+-]?(\d+\.\d*|\.\d+|\d+)([eE][+-]?\d+)?
```

然后用完整匹配判断字符串是否符合这个模式。

### 为什么可行

因为题目要求的合法格式，本来就是一种固定语言模式。

正则做的事情，本质上是：

```text
把所有合法情况一次性描述出来
```

### 复杂度

- 时间复杂度：通常记作 `O(n)`
- 空间复杂度：通常记作 `O(1)` 到 `O(n)`

### 评价

优点：

- 写法非常短
- 对这类“格式匹配题”很直接

缺点：

- 可读性不如手动模拟自然
- 面试里往往不如方法一能体现思考过程

## 方法三：有限状态机（DFA）

### 思路

这题其实很适合抽象成“读字符流”的过程。

每次读到一个字符时：

- 先判断它属于哪一类
- 再根据当前状态，决定能不能转移到下一个状态

比如我们可以把状态拆成：

- 起始状态
- 读过符号的状态
- 读整数部分的状态
- 读小数点的状态
- 读小数部分的状态
- 读指数的状态
- 读指数符号的状态
- 读指数数字的状态

这样一来，整个判断过程就变成了：

```text
查状态表，看当前字符是否合法
```

### 为什么可行

因为“有效数字”本来就是一种有限规则语言。

而有限状态机最擅长处理的，就是这种：

```text
当前允许什么字符、读完后该进入什么状态
```

的问题。

### 一个核心理解

比如当你已经读到了 `e`：

- 下一位可以是 `+/-`
- 也可以直接是数字
- 但不能是 `.`
- 也不能直接结束

这类限制用普通口述能讲，但用状态机可以表达得更严密。

### 复杂度

- 时间复杂度：`O(n)`
- 空间复杂度：`O(1)`

### 评价

优点：

- 结构化最强
- 规则表达非常严谨
- 适合扩展为更复杂的语法检查

缺点：

- 对这题来说偏重
- 面试里手写成本通常高于方法一

---

## 哪个方法最适合面试

### 结论

**最适合面试的是：方法一，手动模拟。**

### 为什么

1. 它最贴合这题的规则拆解过程
2. 每个判断条件都能自然讲出来
3. 代码不长，但信息量足够
4. 出现 bug 时也最好 debug

### 方法二的价值

方法二的价值在于：你可以从“模式匹配”角度重新理解这题。

它适合作为一个更短的补充写法。

### 方法三的价值

方法三更像进阶理解。

它能把这题从“字符串判断题”提升成一个标准的“字符流状态转移”问题。

## 最后总结

这题最重要的主线就是：

1. 它考的不是“像不像数字”，而是格式是否严格合法
2. 真正关键的是符号、小数点、指数这些字符出现的位置
3. 面试最稳的写法是手动模拟，用几个标志位维护当前状态
4. 如果再往上抽象，这题本质上也是一个状态机问题

如果你能把这句复述清楚：

> **这题本质上是在验证字符串是否符合数字格式规则，核心不是字符本身，而是每类字符能不能在当前位置出现。**

那这题就算真的掌握了。
