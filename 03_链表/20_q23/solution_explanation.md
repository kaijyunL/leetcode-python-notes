# LeetCode 23. 合并 K 个升序链表（Merge k Sorted Lists）解析

## 题目描述

给你一个链表数组 `lists`，其中每条链表都已经按升序排列。

请你把这些链表合并成一条新的升序链表，并返回它的头节点。

例如：

```text
lists = [
  1 -> 4 -> 5,
  1 -> 3 -> 4,
  2 -> 6
]
```

合并后得到：

```text
1 -> 1 -> 2 -> 3 -> 4 -> 4 -> 5 -> 6
```

这题的表面是：

```text
把很多条有序链表合成一条有序链表
```

但它真正想考的是：

```text
当“两个有序链表合并”扩展成 “k 个有序链表合并” 时，你会不会做多路归并
```

这就是这题最核心的点。

---

## 先理解这题到底在考什么

如果你已经刷过 `21`，那你会知道：

```text
合并两条有序链表，本质上是每一步只在两个头节点里选更小的那个
```

那 `23` 只是把这个问题放大了一层：

```text
如果现在不是 2 个头，而是 k 个头，该怎么高效地选出当前最小节点？
```

所以这题的本质不是“链表题”，而是：

```text
多路归并（k-way merge）
```

你可以把它理解成：

- `21`：二路归并
- `23`：多路归并

这个视角一旦建立起来，后面的方法三、方法四都会自然很多。

---

## 为什么“每条链表都已经有序”特别关键

因为每条链表本身已经升序，所以在任意时刻：

```text
某条链表里真正有资格被选中的，只可能是它当前的头节点
```

不可能跳过头节点去选后面的节点，因为后面的节点只会更大。

这意味着：

- 每条链表都只需要暴露出一个“候选人”
- 全局最小值一定就在这 `k` 个候选头节点里

所以题目就从：

```text
怎么在所有剩余节点里找最小
```

变成了：

```text
怎么高效地在 k 个当前头节点里反复找最小
```

这正是堆特别擅长的事。

---

## 这题和 `21`、`148` 的关系

这题非常值得和前两题串起来理解。

### 和 `21` 的关系

`21` 是：

```text
合并两个有序链表
```

`23` 是：

```text
合并 k 个有序链表
```

所以 `23` 可以看成两条主线：

- **主线 A**：直接做多路归并，用小根堆维护 `k` 个当前头节点
- **主线 B**：不断把问题降回 `21`，也就是反复做“合并两个有序链表”

### 和 `148` 的关系

`148` 的归并排序，在 merge 阶段其实一直在做：

```text
合并两条有序链表
```

而 `23` 让你进一步看到：

```text
如果不是二路归并，而是多路归并，该怎么设计数据结构或分治结构
```

所以可以这样记：

- **`21`**：二路归并模板
- **`148`**：归并排序里反复用到二路归并
- **`23`**：把二路归并升级成多路归并

---

## 方法一：收集所有值后排序再重建链表

### 思路

最直观的保底做法是：

1. 遍历所有链表，把所有节点值收集进数组
2. 对数组排序
3. 按排序后的结果重新建一条新链表

例如：

```text
[1 -> 4 -> 5, 1 -> 3 -> 4, 2 -> 6]
```

先收集成：

```text
[1, 4, 5, 1, 3, 4, 2, 6]
```

排序后：

```text
[1, 1, 2, 3, 4, 4, 5, 6]
```

再按这个顺序建链表即可。

---

### 代码

```python
class Solution:
    def mergeKLists(self, lists: list[Optional[ListNode]]) -> Optional[ListNode]:
        values = []

        for head in lists:
            cur = head
            while cur:
                values.append(cur.val)
                cur = cur.next

        values.sort()

        dummy = ListNode(0)
        tail = dummy
        for value in values:
            tail.next = ListNode(value)
            tail = tail.next

        return dummy.next
```

---

### 为什么可行

因为数组排序后，所有值的全局升序关系已经确定了。

按这个顺序重建链表，自然就是正确答案。

---

### 复杂度

- 时间复杂度：`O(N log N)`
- 空间复杂度：`O(N)`

其中 `N` 是所有链表节点总数。

---

### 它的不足

它能做，但不是真正值得主记的版本。

因为：

### 1. 没真正利用“每条链表已经有序”

哪怕输入不是有序链表，这个方法也一样能做。

说明它没有用上题目给你的关键信息。

### 2. 没练到链表归并能力

这题更值得掌握的是：

```text
怎么复用原节点，把很多条有序链表原地串成一条更长的有序链表
```

所以真正该主记的还是方法三、方法四。

---

## 方法二：顺序两两合并

### 核心思路

既然你已经会 `21` 题，那最自然的想法就是：

```text
先把第 1 条和第 2 条合并，再和第 3 条合并，再和第 4 条合并……
```

也就是说，我们维护一条当前结果链表 `merged`：

1. 初始时 `merged = None`
2. 依次遍历 `lists` 里的每条链表
3. 每次把当前链表和 `merged` 用 `21` 的方法合并起来

这样最终也能得到答案。

---

## 为什么这个思路很自然

因为 `23` 最直接的降维方式就是：

```text
把“合并 k 个”变成“反复合并 2 个”
```

如果你刚学完 `21`，这是最容易想到的版本。

所以它很适合作为：

- 从 `21` 过渡到 `23` 的桥梁方法
- 帮你建立“多路问题可以不断降成二路问题”的直觉

---

## 用例子走一遍

假设：

```text
lists = [
  1 -> 4 -> 5,
  1 -> 3 -> 4,
  2 -> 6
]
```

### 第 1 步

先把：

```text
None 和 1 -> 4 -> 5
```

合并，得到：

```text
1 -> 4 -> 5
```

### 第 2 步

再把：

```text
1 -> 4 -> 5
和
1 -> 3 -> 4
```

合并，得到：

```text
1 -> 1 -> 3 -> 4 -> 4 -> 5
```

### 第 3 步

再和：

```text
2 -> 6
```

合并，最终得到：

```text
1 -> 1 -> 2 -> 3 -> 4 -> 4 -> 5 -> 6
```

这个过程完全正确，但它会有重复扫描的问题。

---

### 代码

```python
class Solution:
    def mergeKLists(self, lists: list[Optional[ListNode]]) -> Optional[ListNode]:
        merged = None
        for head in lists:
            merged = self.merge_two_lists(merged, head)
        return merged

    def merge_two_lists(
        self,
        a: Optional[ListNode],
        b: Optional[ListNode],
    ) -> Optional[ListNode]:
        dummy = ListNode(0)
        tail = dummy

        while a and b:
            if a.val <= b.val:
                tail.next = a
                a = a.next
            else:
                tail.next = b
                b = b.next
            tail = tail.next

        tail.next = a if a else b
        return dummy.next
```

---

### 为什么可行

因为每一轮都把“当前结果链表”和“下一条有序链表”正确合并了。

如果前一轮结果已经有序，再和一条新的有序链表做 `21` 式合并，合并后的结果仍然有序。

所以最终答案正确。

---

### 复杂度

- 时间复杂度：`O(kN)`
- 空间复杂度：`O(1)`

这里 `k` 是链表条数，`N` 是总节点数。

---

### 它的问题在哪里

问题在于：

```text
结果链表会越来越长，但你还在不断拿这条越来越长的链表去和下一条链表做合并
```

也就是说，前面已经合并过的节点可能被反复扫很多遍。

这就像：

- 先合并 2 条
- 再拿 2 条结果去和第 3 条合并
- 再拿 3 条结果去和第 4 条合并

重复工作比较多。

所以更自然的问题就是：

```text
能不能不要每次都线性扫描 k 个头，也不要让已经合并出的长链表反复参与太多次扫描？
```

这就来到方法三、方法四。

---

## 方法三：小根堆维护 k 个当前头节点（直击多路归并本质）

### 核心思路

如果你想直接从“多路归并”这个题眼切进去，小根堆是最自然的一版。

因为在任意时刻：

```text
全局下一个应该接到答案里的节点，一定就在这 k 条链表当前的头节点里
```

那我们就把这 `k` 个当前头节点放进一个：

```text
小根堆
```

堆顶永远是当前最小节点。

流程就是：

1. 把所有非空链表的头节点放进小根堆
2. 弹出堆顶，也就是当前全局最小节点，接到答案尾部
3. 如果这个节点后面还有下一个节点，就把下一个节点再放进堆
4. 重复直到堆为空

这就是典型的：

```text
多路归并 + 小根堆
```

---

## 为什么这个思路最自然

因为每次真正需要做的决策只有一件事：

```text
从 k 个候选头节点里找出最小的那个
```

而小根堆刚好就是为“反复取最小值”设计的。

如果不用堆，你每次得线性扫描 `k` 个头节点；
用了堆以后，每次取最小值只需要：

```text
O(log k)
```

所以这题和堆的匹配度非常高。

这也是为什么很多题解会直接把它归类为：

```text
优先队列 / 堆 / 多路归并
```

---

## 用例子完整走一遍

假设：

```text
lists = [
  1 -> 4 -> 5,
  1 -> 3 -> 4,
  2 -> 6
]
```

### 初始入堆

把三个头节点放入堆中：

```text
1, 1, 2
```

堆顶是其中一个 `1`。

### 第 1 次弹出

弹出最小值 `1`，把它接到答案链表。

然后把这条链表的下一个节点 `4` 入堆。

堆里变成：

```text
1, 2, 4
```

### 第 2 次弹出

再弹出 `1`，接到答案后面。

把该链表下一个节点 `3` 入堆。

堆里变成：

```text
2, 3, 4
```

### 后续过程

继续重复，每次都：

- 弹当前最小头节点
- 接到答案尾部
- 把该节点所在链表的下一个节点入堆

最终输出：

```text
1 -> 1 -> 2 -> 3 -> 4 -> 4 -> 5 -> 6
```

这就是完整的多路归并过程。

---

### 面试代码

```python
import heapq
from itertools import count


class Solution:
    def mergeKLists(self, lists: list[Optional[ListNode]]) -> Optional[ListNode]:
        heap = []
        order = count()

        for node in lists:
            if node:
                heapq.heappush(heap, (node.val, next(order), node))

        dummy = ListNode(0)
        tail = dummy

        while heap:
            _, _, node = heapq.heappop(heap)
            tail.next = node
            tail = tail.next

            if node.next:
                heapq.heappush(heap, (node.next.val, next(order), node.next))

        return dummy.next
```

---

### 为什么可行

因为在任意时刻，所有尚未处理节点中最小的那个，一定属于某条链表的头节点。

而堆里保存的正是：

```text
每条链表当前还没被取走的那个最前节点
```

所以每次从堆顶取出的节点，一定就是全局当前最小节点。

把它接到答案后，再把它所在链表的新头节点补进堆，
整个不变式就继续成立。

---

### 复杂度

- 时间复杂度：`O(N log k)`
- 空间复杂度：`O(k)`

这是这题最经典的“多路归并 + 堆”复杂度。

---

### 为什么这个方法仍然很值得掌握

虽然我把主推切到方法四，但方法三依然非常重要。

### 1. 它最直接命中题目本质

这题本来就在考：

```text
如何从 k 个当前候选节点里高效选最小
```

小根堆就是最直接的答案。

### 2. 它直接体现“多路归并”

不是把问题降成很多次二路归并，而是直接正面处理 `k` 路。

### 3. 它适合迁移到更多场景

这套写法不只适用于链表，还能迁移到：

- 合并 `k` 个有序数组 / 有序流
- 外部排序
- Top K / 流式最小值维护

### 4. 它是理解方法四之前的好直觉

先想通“全局最小值一定在当前 `k` 个头节点里”，再去看分治怎么把多路问题组织成归并树，会更顺。

所以方法三非常值得作为“题型识别版”掌握。

---

### 容易出错的地方

### 1. 直接把 `ListNode` 放进堆里比较

在 Python 里，如果你直接往堆里放节点对象，值相等时会比较对象本身，通常会报错。

所以常见写法是放：

```python
(node.val, 唯一编号, node)
```

中间这个唯一编号就是为了在值相等时打破比较冲突。

### 2. 弹出节点后忘了把它的下一个节点补进堆

你弹出一个节点，只表示这条链表的当前头节点被消费掉了。

如果它后面还有节点，新头节点就要补进堆，否则这条链表后面的元素就丢了。

### 3. 忘了处理空链表

`lists` 里可能有 `None`，入堆前要先判空。

## 方法四：分治归并（把问题不断降回 `21`）

### 核心思路

如果你特别熟 `21` 和 `148`，那这题还有一条非常漂亮的主线：

```text
把 k 个有序链表不断对半分，分别合并左右两边，最后再把两边结果合并
```

也就是：

1. 把 `lists` 分成左半和右半
2. 递归地把左半合并成一条有序链表
3. 递归地把右半合并成一条有序链表
4. 最后再用 `21` 的 merge 把左右两条结果链表合并

这其实就是：

```text
把多路归并组织成一棵“归并树”
```

---

## 为什么它也很强

因为方法二的问题是：

```text
结果链表越来越长，反复被拿去和下一条链表合并，重复扫描太多
```

而分治会尽量让：

```text
长度相近的链表先两两合并
```

这样每层总工作量是 `N`，一共大约有 `log k` 层，
所以总复杂度就来到：

```text
O(N log k)
```

这和堆法是同一量级。

---

## 用例子走一遍

还是看：

```text
lists = [L1, L2, L3, L4]
```

分治会这样做：

### 第 1 层

先分成：

```text
[L1, L2]
[L3, L4]
```

### 第 2 层

左边先合并成：

```text
merge(L1, L2)
```

右边先合并成：

```text
merge(L3, L4)
```

### 最后一层

再做：

```text
merge( merge(L1, L2), merge(L3, L4) )
```

本质上就是把大量“合并两个有序链表”的工作分层组织起来。

这和 `148` 的归并排序非常像，只不过那里拆的是一条链表，这里拆的是“链表数组”。

---

### 代码

```python
class Solution:
    def mergeKLists(self, lists: list[Optional[ListNode]]) -> Optional[ListNode]:
        if not lists:
            return None
        return self.merge_range(lists, 0, len(lists) - 1)

    def merge_range(
        self,
        lists: list[Optional[ListNode]],
        left: int,
        right: int,
    ) -> Optional[ListNode]:
        if left == right:
            return lists[left]

        mid = (left + right) // 2
        merged_left = self.merge_range(lists, left, mid)
        merged_right = self.merge_range(lists, mid + 1, right)
        return self.merge_two_lists(merged_left, merged_right)

    def merge_two_lists(
        self,
        a: Optional[ListNode],
        b: Optional[ListNode],
    ) -> Optional[ListNode]:
        dummy = ListNode(0)
        tail = dummy

        while a and b:
            if a.val <= b.val:
                tail.next = a
                a = a.next
            else:
                tail.next = b
                b = b.next
            tail = tail.next

        tail.next = a if a else b
        return dummy.next
```

---

### 为什么可行

因为每一层递归都在做同一件事：

```text
先把左半边所有链表合并成一条有序链表，再把右半边所有链表合并成一条有序链表，最后把这两条有序链表正确合并
```

而“合并两条有序链表”本身已经是正确的。

所以从叶子到根层层返回，最终得到的整条链表自然有序。

---

### 复杂度

- 时间复杂度：`O(N log k)`
- 空间复杂度：`O(log k)`

空间复杂度来自递归栈。

---

### 为什么这个方法最适合面试

如果这题你现在只准备记一个最稳的版本，我建议优先记方法四。

### 1. 它最容易从 `21` 迁移过来

本质上你只是在反复调用“合并两个有序链表”，不会突然引入新的数据结构。

### 2. 复杂度和堆法同级

- 时间复杂度：`O(N log k)`
- 空间复杂度：`O(log k)`

既高效，又没有顺序合并那种重复扫描。

### 3. 代码结构稳定、面试里不容易出错

递归边界清晰，`merge_two_lists` 也是成熟模板；相比堆法，还少了 Python 里“值相等时对象不可比较”的细节坑。

### 4. 和题目体系衔接很好

它把 `21` 的二路合并和 `148` 的分治结构真正串了起来，很适合当这一组链表题里的主线路线。

```text
所以如果只主记一种写法，我建议主记方法四：分治归并
```

因为它更直接地命中了这题的“多路归并”本质。

---

## 四种方法的关系

这题四种做法的递进关系很清楚：

- **方法一**：先把所有值拿出来排序重建，属于保底做法
- **方法二**：不断把问题降成 `21`，但顺序合并会有较多重复扫描
- **方法三**：直接做多路归并，用小根堆维护 `k` 个当前头节点，最贴多路归并本质
- **方法四**：把多路问题组织成分治归并树，复杂度也达到 `O(N log k)`，这是主推写法

这题最值得抓住的一句话是：

```text
23 题的本质，不是“链表很多怎么办”，而是“每一时刻全局最小节点一定在 k 个当前头节点里，所以要高效维护这 k 个候选人”
```

一旦这句话真正想通，方法三会很自然；再把这种多路合并过程组织成归并树，方法四也会非常顺。

---

## 复杂度总结

| 方法 | 时间复杂度 | 空间复杂度 | 评价 |
| --- | --- | --- | --- |
| 方法一：收集所有值后排序再重建 | `O(N log N)` | `O(N)` | 最直观，但没用满“每条链表已排序” |
| 方法二：顺序两两合并 | `O(kN)` | `O(1)` | 好理解，是从 `21` 过渡到 `23` 的桥梁 |
| 方法三：小根堆维护 k 个当前头节点 | `O(N log k)` | `O(k)` | 最贴多路归并本质，适合理解题型 |
| 方法四：分治归并 | `O(N log k)` | `O(log k)` | 面试主推，结构稳，和 `21`、`148` 联系最强 |

## 总结
