# LeetCode 4. 寻找两个正序数组的中位数 解析

## 题目描述

给定两个已经升序排列的数组 `nums1` 和 `nums2`，请你返回这两个数组合并后的中位数。

例如：

```text
nums1 = [1, 3]
nums2 = [2]
```

合并后是：

```text
[1, 2, 3]
```

中位数是：

```text
2
```

题目还要求时间复杂度尽量做到：

```text
O(log(m + n))
```

所以这题不能只停留在“真的把两个数组合并起来”。

---

## 先理解题意

这题表面是在找：

```text
两个有序数组合并后的中位数
```

但更关键的理解是：

```text
我们并不一定要真的合并，只要能确定“中间分界线”在哪里就够了
```

因为中位数只和中间附近的元素有关，不需要知道整个合并结果。

---

## 方法一：双指针合并

### 思路

最直接的方法就是模拟归并排序里的 merge 过程：

- 两个指针分别指向 `nums1` 和 `nums2`
- 每次取更小的数放进新数组
- 合并完成后，根据总长度取中位数

如果总长度是奇数：

```python
return merged[mid]
```

如果总长度是偶数：

```python
return (merged[mid - 1] + merged[mid]) / 2
```

---

### 为什么可行

因为两个数组本来就有序，双指针每次拿当前更小值，最终得到的就是完整的有序合并数组。

既然合并结果正确，那么中位数当然也能正确取到。

---

### 复杂度

- 时间复杂度：`O(m + n)`
- 空间复杂度：`O(m + n)`

---

### 这个方法差在哪里

它很好理解，也很适合作为第一步思路。

但它没有满足题目想考的重点：

```text
如何把时间复杂度压到对数级别
```

所以还需要继续思考更优做法。

---

## 方法二：二分查找分割点（面试主推）

这是这题最经典、也最适合面试的方法。

要先注意一件事：

```text
这题不是在数组里找某个数，
也不是像 q35 / q875 那样找“第一个合法值”，
而是在找“正确的分割点”
```

也就是说，我们想把两个数组一起切成：

- 左半部分
- 右半部分

并且满足：

1. 左半部分的元素个数正确
2. 左半部分所有数都小于等于右半部分所有数

只要这两个条件成立，中位数就出来了。

---

## 核心想法

假设我们在 `nums1` 里切一刀，左边取 `i` 个数。

那么为了让左半部分总长度固定，`nums2` 左边就必须取 `j` 个数。

设：

```python
total_left = (m + n + 1) // 2
```

那么：

```python
j = total_left - i
```

也就是说：

```text
只要 i 确定了，j 就自动确定
```

所以整道题其实就变成了：

```text
在 nums1 上二分查找合适的 i
```

---

## 为什么 `total_left = (m + n + 1) // 2`

这是个很关键的小细节。

如果总长度是奇数，我们希望：

```text
左半部分比右半部分多一个元素
```

比如总长度是 `5`，那左边应该有 `3` 个。

如果总长度是偶数，我们希望：

```text
左右两边一样多
```

比如总长度是 `6`，那左边应该有 `3` 个。

所以统一写成：

```python
(m + n + 1) // 2
```

这样奇偶都兼容。

---

## 为什么只在更短的数组上二分

这也是这题非常重要的一点。

我们先保证：

```python
len(nums1) <= len(nums2)
```

这样做有两个原因：

### 1. 二分范围更小

我们只在 `nums1` 上找 `i`，当然希望它更短，这样复杂度就是：

```text
O(log(min(m, n)))
```

---

### 2. 更容易保证 `j` 不越界

因为：

```python
j = total_left - i
```

如果在长数组上乱切，另一边的 `j` 更容易跑出边界。

先把较短数组放到前面后，整个分割过程会更稳定，也更容易写对。

---

## 正确分割需要满足什么条件

切分后，四个边界值是：

```text
nums1_left   = nums1[i - 1]
nums1_right  = nums1[i]
nums2_left   = nums2[j - 1]
nums2_right  = nums2[j]
```

如果要让左半部分所有数都小于等于右半部分所有数，只需要满足：

```python
nums1_left <= nums2_right
nums2_left <= nums1_right
```

---

## 为什么只看这四个数就够了

因为两个数组本身已经各自有序。

所以：

- `nums1_left` 是 `nums1` 左半部分最大值
- `nums1_right` 是 `nums1` 右半部分最小值
- `nums2_left` 是 `nums2` 左半部分最大值
- `nums2_right` 是 `nums2` 右半部分最小值

左半部分里真正可能“越界”的，只会是左边最大值。

右半部分里真正可能“太小”的，只会是右边最小值。

所以只需要检查这四个边界值的交叉关系，不需要检查更里面的元素。

---

## 边界怎么处理

如果切分刚好落在数组最左边或最右边，会出现某一侧没有元素的情况。

比如：

- `i == 0`，说明 `nums1` 左边没有元素
- `i == m`，说明 `nums1` 右边没有元素

这时可以把不存在的边界设成：

```python
float("-inf")
float("inf")
```

这样我们就不用额外写很多特判，代码会更整洁。

---

## 找到正确分割后怎么得到中位数

如果总长度是奇数：

```python
return max(nums1_left, nums2_left)
```

因为左半部分比右半部分多一个数，中位数就是左半部分最大值。

如果总长度是偶数：

```python
left_max = max(nums1_left, nums2_left)
right_min = min(nums1_right, nums2_right)
return (left_max + right_min) / 2
```

因为中位数是中间两个数的平均值。

---

## 二分时怎么移动

如果：

```python
nums1_left > nums2_right
```

说明 `nums1` 左边拿多了。

因为 `nums1` 左边最大的数都已经比 `nums2` 右边最小的数大了，切分点必须往左移：

```python
right = i - 1
```

反过来，如果不满足上面这种情况，说明 `nums1` 左边拿少了，应该往右移：

```python
left = i + 1
```

---

## 一个小例子

例如：

```text
nums1 = [1, 3, 8]
nums2 = [7, 9, 10, 11]
```

总长度是 `7`，所以：

```python
total_left = 4
```

如果某次二分取到：

```text
i = 2
j = 2
```

那么分割就是：

```text
nums1: [1, 3] | [8]
nums2: [7, 9] | [10, 11]
```

这时：

- `nums1_left = 3`
- `nums1_right = 8`
- `nums2_left = 9`
- `nums2_right = 10`

会发现：

```text
nums2_left = 9 > nums1_right = 8
```

说明 `nums1` 左边拿少了，切分点要往右移。

如果再移动到正确位置，就能得到合法分割。

---

## 复杂度

### 方法一：双指针合并

- 时间复杂度：`O(m + n)`
- 空间复杂度：`O(m + n)`

### 方法二：二分查找分割点

- 时间复杂度：`O(log(min(m, n)))`
- 空间复杂度：`O(1)`

---

## 最适合面试的方法

最适合面试的是：

```text
方法二：二分查找分割点
```

原因是：

1. 这题最核心的考点就是能不能从“合并数组”跳到“寻找正确分割”
2. 二分写在较短数组上，复杂度刚好满足题目要求
3. 思路虽然不如方法一直接，但一旦理解，代码其实很稳定

---

## 面试里建议怎么解释

可以按这个顺序说：

1. 真的合并可以做，但只能做到 `O(m + n)`
2. 中位数只和中间分界线有关，不需要完整合并
3. 设 `nums1` 左边取 `i` 个，`nums2` 左边就取 `total_left - i` 个
4. 只要左半部分长度正确，而且左边最大值不大于右边最小值，分割就成立
5. 因为 `i` 的搜索范围有序，所以可以在较短数组上二分

如果你想把它和前面几道题联系起来，可以这样记：

```text
q35 / q875 是找某个边界，
q4 是找一个“让左右分割恰好成立”的切分位置
```

这两类题都用了二分，但二分对象并不一样。
