## 如何阅读这个仓库

如果你是第一次看这个仓库，建议按下面顺序使用：

1. 先按专题进入目录，比如 `03_链表`
2. 再按题号进入对应题目目录，比如 `03_链表/01_q206`
3. 优先看对应的 Markdown 讲解，先建立题目思路和方法分层
4. 再按“方法一 / 方法二 / 方法三”的顺序阅读代码，从简单方法看到最优解法
5. 最后结合复盘记录、可视化材料或模板题做归纳

如果某道老题还没有独立讲解 Markdown，再回退到先看 `brute_force.py`、`solution.py`、`optimal.py` 等代码文件。

## 文件产出与命名约定

常见文件类型：

- `solution_1_xxx.py` / `solution_2_xxx.py`：按方法顺序拆开的独立可执行 Python 文件
- `brute_force.py`：朴素解法，通常用于和优化方案对比
- `optimal.py`：最优或主推解法
- `*.md`：题解、复盘、学习笔记、总结文档
- `*.html`：可视化或交互式讲解页面

后续新增或重写题解时，推荐遵循以下命名方式：

- 多种方法的代码文件使用 `solution_<编号>_<方法关键词>.py`
- 编号要和 Markdown 中的“方法一 / 方法二 / 方法三”严格对应
- 代码文件首行可用简短中文注明方法，例如：`# 方法1：暴力枚举`
- 讲解文档和代码文件分开维护，不把大段题解直接塞进 Python 文件里

## 刷题协作原则

当我说“帮我理解 LeetCode 第 x 题”时，默认按**刷题讲解模式**处理，而不是只给最终答案。

具体约定如下：

1. **循序渐进讲解**
   - 先帮助我理解题意、样例、约束和直觉思路
   - 再从简单/暴力方法开始，逐步推进到更优方法
   - 方法数量按题目本身决定，不强行固定成 2 种、3 种或 4 种

2. **先讲解 Markdown，再拆代码文件**
   - 先把题解讲解保存成对应工作目录下的 Markdown 文档
   - 再把每种方法拆成独立、可执行的 Python 文件
   - 讲解和代码分开，方便复习和单独运行

3. **代码注解用中文，但只保留必要注释**
   - 注释以中文为主
   - 不写太多无用、逐行翻译式注释
   - 只有在边界处理、关键转移、非直觉技巧等确实必要时才加注释

4. **从简单方法到最优解法依次给出**
   - 先给朴素/暴力解法，说明它为什么可行、为什么会慢
   - 再给改进解法和最优解法，明确每一步优化点
   - 讲清楚时间复杂度、空间复杂度，以及思路切换的原因

5. **明确指出最适合面试的方法**
   - 在解析文档中明确写出“哪个方法最适合面试”
   - 对最适合面试的方法，必须使用面试现场最适合写的代码版本：简洁、自然、容易复现，不为了教学展开而写复杂版本
   - 对最适合面试的方法讲得更细：为什么它更稳、复杂度如何、边界怎么想、面试里该怎么解释
   - 如果最优解不一定最适合面试，也要把原因说清楚

6. **面试版讲解要把推导过程说清楚，而不是只报结论**
   - 不能只给结论或只贴模板名称，必须把思路是怎么一步步得到的讲清楚
   - 要优先解释“核心思路是怎么想到的 / 关键步骤为什么成立 / 为什么这样处理边界、顺序、条件或剪枝”，而不是只说“这是某某模板”
   - 只要某个变量、循环、条件或状态符号承担了理解上的关键作用，就要明确说明它表示什么、为什么这样写
   - 如果一道题有多种做法，要说明它们之间的递进关系：朴素方法为什么可行、为什么慢，优化方法到底优化了哪一步
   - 对最适合面试的方法，要额外讲清：核心思路、关键细节、容易出错的地方，以及面试里应该怎么解释
   - 如果某一步只写抽象结论会让人难以真正理解，就应该补一个小例子把中间过程展开
   - 默认目标是：让读者看完讲解后，不只是记住答案，而是能自己把核心思路复述出来

7. **文件命名风格与 `01_q01` 保持一致**
   - 后续新增或重写题目时，题目目录和文件命名风格默认对齐 `01_q01` 的组织方式
   - 如果遇到历史遗留命名不一致，优先在新增内容中保持统一，不再继续扩散旧命名风格
